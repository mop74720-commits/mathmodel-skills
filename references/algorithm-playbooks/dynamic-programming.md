# Dynamic Programming Playbook

动态规划用于具有明确阶段/状态、最优子结构与可控制状态转移的问题。先证明状态压缩成立，再决定是否使用 DP；不要把“问题有很多步骤”自动等价为动态规划。

## 1. 结构识别

- Stage：决策按时间、位置、容量、子集大小等推进。
- State：必须包含决定未来收益/可行性的充分信息。
- Action / transition：从当前状态到下一状态的合法决策。
- Value recurrence：未来最优值只依赖当前状态，而不是遗漏的完整历史。

如果无法给出清晰 Bellman recurrence，应先回到问题结构，而不是直接写三重循环。

## 2. 常见形式

- 资源/背包：容量状态；检查 0-1 与完全背包更新方向。
- 序列：LCS、编辑距离等二维状态。
- 区间 DP：状态为区间边界，注意划分顺序。
- Bitmask / subset DP：TSP 等小规模组合问题，复杂度通常呈指数增长，先估算状态数。
- 时间/库存 DP：连续状态离散化时必须报告网格误差。

## 3. 设计流程

1. 写出状态语义，而不是先写数组下标。
2. 明确初始条件、不可达状态与终止条件。
3. 推导 recurrence，并用手工小实例逐层核对。
4. 估算时间/空间复杂度；必要时滚动数组、稀疏状态、剪枝或分解。
5. 若需要恢复策略，保存 predecessor/action，不只保存最优值。
6. 对连续状态离散 DP 做网格加密和策略稳定性检查。

## 4. 与其他方法的边界

- 线性/整数约束自然且 MILP 可解：MILP 可能更简洁并提供 gap/certificate。
- 状态空间巨大但图结构明显：考虑 shortest path / label-setting / network formulation。
- Bellman 方程连续且随机：可能进入 MDP / stochastic control；需要额外概率转移合同。
- 近似 DP / RL 只有在精确 DP 确实不可行且有验证基准时升级。

## 5. 验证

- 小规模 brute force 与 DP 值完全一致。
- 检查状态是否遗漏历史依赖；构造两个“同状态不同历史”反例尝试攻击 Markov/充分状态假设。
- 边界容量、空集、单元素、最大状态做测试。
- 优化后的滚动/剪枝实现与未优化版本在小实例上等价。

论文中应给出状态定义、递推关系、边界、复杂度和验证，不把代码循环本身当数学模型。
