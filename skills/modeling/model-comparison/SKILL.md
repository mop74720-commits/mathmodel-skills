# model-comparison

## Trigger

- 事件：`MODELS_NEED_COMPARISON`。
- 用户明确点名本能力时也可直接调用。
- 本 Skill 只解决局部问题；比赛阶段、时间预算、是否放弃某题仍由 Coach 决定。

## Scope

只用于候选模型已经达到可运行或至少可定量评价的阶段。它不是文献式“优缺点罗列”，而是可复现比较。

## Inputs

- 候选模型合同
- Baseline
- 统一数据/场景
- 评价指标
- 已有运行结果或可运行命令

## Procedure

1. 冻结比较协议：相同数据切分/场景、相同评价口径、相同约束、相近计算预算；不能让一个模型使用额外信息。
2. 区分主指标、硬约束指标和次级指标。优化问题优先检查可行性，再比较目标值；预测问题同时看泛化误差与业务/物理边界。
3. 对随机模型使用多次独立运行或可复现重采样；报告中心趋势与离散性。确定性模型无需为了“形式统一”重复跑无意义次数。
4. 只有在统计假设适用时才做显著性检验；样本配对结构存在时使用配对方法，不能机械套 t 检验。
5. 加入复杂度维度：运行时间、内存、参数数量、解释成本、实现风险，但不要把这些无依据地加权成单一分数。
6. 识别 Pareto 情况：若一个模型更准但明显更慢/更难解释，给出条件式推荐而不是伪造唯一赢家。
7. 记录被淘汰模型及淘汰理由，避免后续论文与代码重新引用旧结果。

## Outputs

- 公平比较表
- 主结论与条件式推荐
- 差异不确定性/显著性（适用时）
- 淘汰/保留理由

## Checks

- 所有模型使用相同事实基线
- 比较前先核对可行性和约束
- 没有把统计显著等同于实际重要
- 没有用测试集反复调参

## Failure

- 差异主要来自数值误差：转 `NUMERICAL_SUSPECT`
- 差异对随机种子/场景不稳：转 `RESULT_UNSTABLE`
- 已确定主模型但需冻结合同：转 `MODEL_CONTRACT_MISSING`

## Handoff

返回推荐模型与不确定性；最终是否升级主模型仍由 Coach 决定。

统一回执字段：`status / inputs_used / outputs_written / key_findings / risks / qa_status / handoff`。Skill 可以建议下一个事件，但不能自行切换比赛阶段。
