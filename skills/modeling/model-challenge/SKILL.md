# model-challenge

## Trigger

- 事件：`MODEL_NEEDS_CHALLENGE`。
- 当模型已基本形成，但需要判断是否过度复杂、创新是否真实、某组件是否必要，或准备进入重要实现/论文阶段前调用。

## Scope

不是重新做一遍 model-selection，而是对“已经选中的模型”进行结构性压力测试，回答：每个组件为什么存在，删掉或替换后会发生什么。

## Inputs

- 当前 model contract
- Baseline 与候选结果（如有）
- 关键指标、约束与验证方案
- 计算成本/解释成本
- 已宣称的创新点

## Procedure

1. **简化测试**：逐项检查复杂组件、额外状态变量、额外模型层、复杂算法；问“删除后是否仍能回答题目核心问题”。
2. **合理性测试**：检查每个核心假设是否与题面/数据/领域机制一致；复杂模型不能用更强且更脆弱的假设换取表面精度。
3. **替换测试**：为关键组件寻找一个更简单或机制不同的替代，比较结果、可解释性、实现风险与验证难度。
4. **去掉测试**：真正移除可疑组件或在概念上构造消融，观察哪些结论失效；若几乎不影响核心结论，则该组件不应被包装成核心创新。
5. **解释测试**：要求用少量变量、公式和因果链解释模型为什么产生关键结果；若只能“黑箱报分”，标记解释风险。
6. **创新真实性测试**：创新必须落在问题表示、约束/目标、算法策略、验证设计或数据处理上，并能指出相对 Baseline 的可验证增量。
7. 形成保留/降级/删除/待实验验证四类结论，不使用无依据百分制评分。

## Outputs

- 模型组件必要性表
- 简化/替换/消融候选
- 创新点真实性与证据缺口
- 推荐保留、降级或删除的组件
- 需要实验验证的最小问题列表

## Checks

- 每个核心组件都有“存在理由”
- 复杂度带来的收益可验证
- 创新点不是模型名堆叠
- 删除/替换测试不会被主观口头结论代替
- 没有把“更复杂”写成“更高级”

## Failure

- 需要真实实验才能裁决：转 `MODELS_NEED_COMPARISON` 或 `EXPERIMENTS_UNTRACKED`
- 发现核心假设不可靠：转 `ASSUMPTION_WEAK`
- 发现 model contract 不完整：转 `MODEL_CONTRACT_MISSING`

## Handoff

挑战完成后可转 `MODELS_NEED_COMPARISON`、`NEED_LOW_RISK_IMPROVEMENT` 或 `MODEL_CONTRACT_MISSING`。Coach 决定是否值得花时间执行额外消融。
