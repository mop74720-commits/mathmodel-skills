# robustness

## Trigger

- 事件：`RESULT_UNSTABLE`。
- 用户明确点名本能力时也可直接调用。
- 本 Skill 只解决局部问题；比赛阶段、时间预算、是否放弃某题仍由 Coach 决定。

## Scope

鲁棒性关注“结论能否承受合理变化”，比单参数灵敏度更强调组合扰动与最终决策稳定。

## Inputs

- Final/Baseline 候选
- 不确定性来源清单
- 允许场景/参数范围
- 关键结论或策略

## Procedure

1. 定位不稳定来源：算法随机性、样本抽样、测量噪声、参数估计、场景/需求变化、边界条件、模型结构。
2. 为最重要的 1–3 类不确定性设计压力测试；不要为了“全面”生成大量无意义组合。
3. 随机算法使用多 seed；统计模型可用重采样/交叉验证；优化可做需求/成本情景；机理模型可做边界和参数区间。
4. 记录每次场景的核心数值和最终决策（排名、选址、策略、是否可行），重点看决策翻转率或可行率。
5. 构造合理的边界/坏情景测试，而不是只在基准点附近小扰动；但不得使用题面不允许的超域数据制造“鲁棒”。
6. 若存在少量失效情景，明确鲁棒域/失效条件，并评估是否需要稳健优化、保守策略或限制声明。
7. 把纯数值不稳定与现实场景不稳定区分开；前者交 `numerical-check`。

## Outputs

- 鲁棒性场景表
- 决策稳定性/可行率/性能分布
- 失效边界或鲁棒域
- 必要的模型/论文限制

## Checks

- 场景扰动有现实或题面依据
- 报告了失败而不是只报最佳场景
- 核心结论与数值波动分开评价
- 随机性有足够重复支持结论

## Failure

- 不稳定来自数值算法：转 `NUMERICAL_SUSPECT`
- 不稳定来自模型结构：转 `MODEL_UNCERTAIN`
- 稳定性足够且需写论文解释：转 `RESULT_NEEDS_INTERPRETATION`

## Handoff

返回稳定性等级和失效条件，不把“鲁棒”当绝对结论。

统一回执字段：`status / inputs_used / outputs_written / key_findings / risks / qa_status / handoff`。Skill 可以建议下一个事件，但不能自行切换比赛阶段。
